# v0.6.5：被截断的 `<summary>` 不再算作任务完成

**日期**：2026-10-28
**上下文**：v0.6.4 之后。JC 报「这个对话为什么会自己断，我明明已经增加了外层自动继续循环」——外层续跑（Goal Mode / 连续任务）明明在，会话却在中途静默收工。
诊断落在 `managed-ga/code/ga.py` 的 `do_no_tool`；修完顺带发现 main 上的补丁链本身不能回放，一起补上。

## 病症

`do_no_tool` 是一轮没有工具调用时的兜底判定：返回 `(next_prompt=None, should_exit)` 就等于告诉 `agent_loop` 本轮 `CURRENT_TASK_DONE`，会话结束。
v0.6.4 之前它是这样识别「上游把回复截断了」的：

```python
if '[!!! 流异常中断' in content[-100:] or '!!!Error:' in content[50:][-100:] or (content.endswith('</summary>') and len(content) < 100):
```

第三项只认 `content.endswith('</summary>')`。而**被截断的摘要永远不会有闭合标签**——于是最该重试的形态恰恰是唯一逃过检测的形态：它往下走到兜底
`next_prompt=None`，外层看到的是一次正常收工。用户侧的表现就是「说到一半自己断了」，而续跑机制完全没被触发过，因为根本没把它当异常。

## 证据

会话库 `~/Library/Application Support/app.galley/workbench.db` 的 `messages` 表（`role / tool_calls / content / final_answer`），
`tool_calls LIKE '%no_tool%'` 即本轮未调用工具、被判结束：

- 以 `<summary>` 开头的 `no_tool` 收工点 **879** 个；
- 其中 `</summary>` 缺失的 **17** 个（1.9%）；
- 这 17 个**无一例外**没有任何后续正文——`<summary>` 是收尾段，它没闭合说明生成在上游就断了。

所以「以 `<summary>` 开头 + 没有 `</summary>`」是 100% 精确的截断信号，不需要按长度或结尾字符猜。

## 改法

分支 `fix/truncated-summary-0.6.5`，`managed-ga/patches/1002-managed-truncated-summary-not-final.patch`：

```python
_truncated_summary = (content.lstrip().startswith('<summary>')
                      and '</summary>' not in content)
if ('[!!! 流异常中断' in content[-100:] or '!!!Error:' in content[50:][-100:]
        or _truncated_summary or (content.endswith('</summary>') and len(content) < 100)):
    return (yield from self._retry_or_exit("[ERROR] Incomplete response. Regenerate and tooluse."))
```

并入 1.4 分支（与已有的流异常中断 / 上游错误串同一条重试路径），走 `_retry_or_exit`：有限次重试（默认 6）后 `should_exit`，不会无限重试。

两条反例一起守住，避免把正常收尾误判成截断：

- 已闭合 `<summary>…</summary>` + 后附正文 → 不拦；
- 正文里只是**提到** `<summary>`（在前面、或只是引用）→ 不拦（`lstrip().startswith` 只认开头）。

## 回归

`test_no_tool_fix.py` 新增 7 例（4 条未闭合摘要 + 3 条反例），支持 `GA_CODE_DIR` 指向已装版本：

- 新 payload：**17/17 通过**；
- 旧 payload（已装的 v0.6.4）：13 通过、4 失败，失败的正好是那 4 条新用例——说明测试确实钉住了这次的差异，不是自证。

## 顺带：main 的补丁链原本不能回放

为了让 1002 的行号可靠，本地按 `scripts/build-managed-ga.sh` 的方式从上游 `f308ee7`（tree `85f99e16`，与 manifest 一致）重放全部补丁，结果 **1001 打不上**：

- `17d75b9a`「stop premature turn end on leaked upstream tool-call markers」（DSML 保留标记）只改了 `managed-ga/code/ga.py`（+28 行），**没有留 patch 文件**；
- 而 `1001` 的 diff 把那段代码当作 context。于是 `git apply` 在 `1001` 必然失败，`managed-ga/code` 从此只能手改、无法重建。

CI 之所以没发现：`check-managed-ga-payload.mjs` 只校验补丁文件存在与命名，**不校验回放**；`release.yml` / `check.yml` 都不调用 `build-managed-ga.sh`。

裁决：把缺的那一环补成补丁，而不是把 1001 的 context 删掉了事——删 context 只能让链条「能打上」，不能让它「重现仓库现状」。

- 新增 `1000a-managed-dsml-marker-not-tool-call.patch`（即 `17d75b9a` 的 diff，路径改写为 `a/ga.py`），插在 `1000` 与 `1001` 之间；
  其 blob 索引 `72b0b3d2..667912e5` 与 1001 的 `667912e5..884d3185` 正好接上，是这条链上确实缺的那一环；
- `manifest.json` / `manifest.md` 一并登记；顺手补上 `1001` 在 `manifest.md` 表格里本来就缺的那一行。

结果：**31 个补丁全链回放，与仓库 `managed-ga/code` 逐字节一致**。这一点以后应该进 CI（回放校验，而不只是文件存在性校验）。
