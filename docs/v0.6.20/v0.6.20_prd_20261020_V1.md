## 1. 背景与问题

### 1.1 现象

用户在长会话中频繁遇到"干几步就断"，需要不断手动输入"继续"：

- 「新版本全体验证测试」会话（gemini-4-argon，708 轮）中用户输入"继续" **12 次**；
- 诊断会话第 1 轮直接返回 `!!!Error: HTTP 503`；
- 其他对话偶发同类中断。

### 1.2 数据证据

近 3 天模型调用日志（52 个 response 文件）错误分布：

| 错误类型 | 出现次数 | 涉及模型 |
|---|---|---|
| `SSE Upstream request failed` / `connection reset by peer` | 90+ | grok-4.7 / ccai-grok-4.7 |
| `HTTP 400 upstream rejected` | 92 | deepseek-v4.1-flash |
| `HTTP 502 / 524 All available accounts exhausted` | 85 | gemini-4-argon（账号池耗尽） |
| `HTTP 503 Service temporarily unavailable` | 170 行 / 8 文件（单文件最高 97 次） | kimi-k3 等（中转网关） |

「新版本全体验证测试」12 次"继续"逐一核对：**4 次**前一条是上游错误（`[Error: Claude refusal]`）；**8 次**是模型输出纯文本总结而未带工具调用，引擎判定 `CURRENT_TASK_DONE` 正常结束（软中断，非报错）。

### 1.3 根因诊断（已核实源码，行号为 v0.6.2 实机复核值）

**现有重试机制是生效的，但只覆盖单次请求：**

`llmcore.py` `_stream_with_retry`（:499-580）：`for attempt in range(max_retries + 1)`，覆盖 {408,409,425,429,500,502,503,504,520-524,529} 及 SSE 断流，退避 3s→6s→12s…封顶 30s（`_delay` :503-505）。用户所有模型均配 `max_retries: 9`、`max_retry_after: 600`。

**缺口在请求级重试耗尽之后：**

请求级重试耗尽后引擎 yield `!!!Error: ...` 作为本轮回答 → `agent_loop.py:78` 无工具调用 → 自动塞入 `no_tool` 伪工具 → `ga.py:522` `do_no_tool` 检测到错误 → `_retry_or_exit`（`ga.py:497`）**最多重试 3 次且无任何退避等待**，故障窗口内 3 次瞬发重试全部失败 → `should_exit=True` 整轮结束。此后无任何外层机制自动续跑，只能用户手动"继续"。

**为什么 9 次重试会打穿**：中转网关的 503 故障窗口常为分钟级；9 次 × 封顶 30s ≈ 覆盖 2~3 分钟，窗口更长即打穿。用户稍后手动"继续"时窗口已过，所以"继续一下就好了"。

**Goal 模式现状**（`reflect/goal_mode.py`，113 行）：纯时间驱动，`budget_seconds` 耗尽才收口，prompt 明示"无法宣告完成"——目标完成也继续空转、超时未完成也停。

### 1.4 与同类 agent 的差距

其他 agent 的"不断"来自 Galley 缺失的三层：轮次级自动续跑、SSE 断流后续传（而非整轮作废）、失败后自动切换备用模型/账号。

## 2. 目标与非目标

**目标**
- G1 请求级退避曲线可配置，支持档位表（用户指定：10s → 30s → 2min 逐级拉长轮询）
- G2 轮次级自动重试：错误轮结束后自动退避重发整轮，可配次数，无需用户手动"继续"
- G3 Goal 模式改为完成驱动：完成即停、超时保底
- G4 全程向后兼容：不配置新参数时行为与现状一致

**非目标**
- 不改中转网关逻辑（用户另行处理池子健康/轮询换号）
- 不做 SSE 断流续传（可作为后续版本）
- 不做自动切换备用模型（可作为后续版本）

## 3. 需求详述

### R1 请求级退避曲线配置化（P0）

**现状**（`llmcore.py:516-505`）：
```python
def _delay(resp, attempt):
    ...
    return None if ra and ra > cap else max(0.5, ra or min(30.0, 3.0 * (2 ** attempt)))
```

**改为**：
```python
def _delay(resp, attempt):
    try: ra = float((resp.headers or {}).get("retry-after"))
    except: ra = None
    if ra and ra > cap: return None
    if ra: return max(0.5, ra)
    schedule = getattr(sess, 'retry_schedule', None) or [3, 10, 30, 60, 120]
    return schedule[min(attempt, len(schedule) - 1)]
```

配置读取（`llmcore.py:896` 附近 session 初始化处）：
```python
self.retry_schedule = cfg.get('retry_schedule')  # 例: [10, 30, 120]
```

模型配置高级选项新增 `"retry_schedule": [3, 10, 30, 120, 300]`。

**验收**：
- 不配置 `retry_schedule` 时行为与现状一致（默认档 [3,10,30,60,120] 不劣于原曲线）；
- 配置后按档位表退避；
- `retry-after` 头优先级不变。

### R2 轮次级自动重试（P0，核心缺口）

**现状链路**：`llmcore.py:521` yield `!!!Error:` → `agent_loop.py:78` 塞 `no_tool` → `ga.py:522` 检测 → `ga.py:497` `_retry_or_exit` 3 次瞬发即弃 → 无人接管。

**改法**（`ga.py:497-511` 附近）：

```python
def _retry_or_exit(self, prompt):
    self._empty_ct = getattr(self, '_empty_ct', 0) + 1
    max_turn_retries = int(getattr(self, 'turn_retry_max', 6))   # 原硬编码 3
    if self._empty_ct >= max_turn_retries:
        return StepOutcome({}, should_exit=True)
    backoff = [10, 30, 60, 120, 300]
    d = backoff[min(self._empty_ct - 1, len(backoff) - 1)]
    yield f"[Info] 上游错误，{d}s 后轮次级重试 ({self._empty_ct}/{max_turn_retries})...\n"
    end = time.time() + d
    while time.time() < end:
        sess = getattr(self, 'client', None)
        if sess and getattr(sess, 'should_stop', None) and sess.should_stop():
            return StepOutcome({}, should_exit=True)
        time.sleep(1)
    return StepOutcome({}, next_prompt=prompt)
```

**必须配套的改动**（回归风险最高点）：
- **成功后清零**：任何真实工具调用成功时 `_empty_ct = 0` 复位（`agent_loop.py` 工具分发处，约 :76，即 `if tool_name == 'no_tool': pass` 的 else 分支）。**漏改此项的后果**：计数器跨任务累积，后续一次普通空响应会被误判为"第 N 次失败"导致整轮莫名提前退出。
- 次数可配：session 初始化处（`llmcore.py:896` 附近）读 `cfg.get('turn_retry_max', 6)` 挂到 handler。
- 确认 `ga.py` 顶部有 `import time`。

**覆盖能力**：6 轮 × 退避 ≈ 8 分钟故障窗口，与手动"继续"等效但无需人工。

**验收**：
- 模拟 503 打穿请求级重试后，引擎自动按 10/30/60s 退避重发整轮，恢复后续跑任务，用户零干预；
- 用户中途停止（should_stop）立即退出，不多发请求；
- 正常任务（无错误）行为完全不变。

### R3 Goal 模式完成驱动（P1）

**现状**（`reflect/goal_mode.py`）：`check()` 纯按 `budget_seconds` 判断收口；CONTINUATION_PROMPT 写死"无法宣告完成"。

**改法**：

1. `check()` 中 `_load()` 之后加完成信号检查：
```python
if state.get('completion_signal'):
    if state.get('turns_used', 0) >= 2:   # 防过早完成
        state['status'] = 'done_completed'
        state['end_time'] = time.time()
        _save(state)
        return '/exit'
    # 不足 2 轮：忽略 signal，继续唤醒
```

2. CONTINUATION_PROMPT 将"无法宣告完成"段替换为完成协议：
```
当你判断 objective 已完整达成时：
1. 在 state 文件写入 "completion_signal": {"verdict": "完成判定", "evidence": "客观证据列表"}
2. 证据必须可验证（测试结果/产物清单/逐条对照原始需求）
虚假完成声明会被后续检验推翻并浪费预算，宁缺毋滥。
```

**验收**：
- agent 写 completion_signal 且 turns_used ≥ 2 → Goal 退出，剩余预算不消耗；
- 首轮即写 signal → 被忽略继续唤醒；
- 预算耗尽仍未完成 → 维持原收口行为（超时保底）。

## 7. 风险与说明

- **升级覆盖**：直接改 app 包内文件会被 Galley 升级覆盖，必须走 patch 机制或自有 runtime；
- **T3 清零遗漏**是本方案最大的回归风险点，需重点 review；
- 轮次级退避期间 UI 宜显示倒计时状态（如"上游错误，60s 后自动重试 2/6"），避免用户误以为卡死——UI 部分需前端配合，列为后续增强；
- 中转侧（用户自管）同步改进：池子健康检查 + 失败换号 + 429 `retry-after` 头支持，与客户端重试形成双侧防护。
